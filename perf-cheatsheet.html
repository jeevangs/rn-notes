Diagnosing jank — the flow

A repeatable order for finding a frame-drop cause instead of guessing.

  1. Read the dual FPS (Perf Monitor). JS low + UI fine → JS-thread work (logic / re-renders). UI low too → native / layout (long lists, overdraw, large images). See JS vs UI thread.
  2. If JS-bound, capture a Hermes sampling profile and read the flame — the widest frame is the hot path. See reading a flamegraph.
  3. Match the hot path to a cause:
    • An effect / subscription re-running every render → stale closure / missing stable ref.
    • One update re-rendering a whole list → render fan-out.
    • Heavy synchronous work (large JSON.parse, unmemoized derivation) blocking the JS thread.
  4. Apply the fix: stable ref or functional setState for stale closures · per-id selectors for fan-out · useMemo or InteractionManager to defer heavy work · move animations to the UI thread (Reanimated / native driver).

If JS looks idle but frames still drop, the cost is on the UI / native side — profile with Xcode Instruments (Time Profiler) or Perfetto instead of the Hermes profiler.

Inline literal props (anti-pattern)

avoid
<Row
  item={item}
  style={{ padding: 12 }}                       // new object every render
  onPress={() => navigation.navigate('Detail')} // new function every render
  meta={['a', 'b']}                              // new array every render
/>
prefer
const META = ['a', 'b'];                   // hoist constant
const onPressRow = useCallback(             // stable function
  () => navigation.navigate('Detail'),
  [navigation]
);

<Row item={item} style={styles.row} onPress={onPressRow} meta={META} />

const styles = StyleSheet.create({ row: { padding: 12 } });

Any {...} literal in props creates a new identity each render — breaks memo equality on the child.

memo on child

const Row = memo(function Row({ item, onPress }: {
  item: Item;
  onPress: (id: string) => void;
}) {
  return (
    <Pressable onPress={() => onPress(item.id)}>
      <Text>{item.title}</Text>
    </Pressable>
  );
});

// Custom comparison if needed
const Row2 = memo(
  function Row2({ item }: { item: Item }) { return <Text>{item.title}</Text>; },
  (prev, next) => prev.item.id === next.item.id && prev.item.title === next.item.title
);

Stable ref pattern

Use a ref to access the latest callback inside an effect that should not re-subscribe.

function useSocket(url: string, onMessage: (m: Msg) => void) {
  const onMessageRef = useRef(onMessage);
  onMessageRef.current = onMessage;  // updates every render — cheap

  useEffect(() => {
    const ws = new WebSocket(url);
    ws.onmessage = (e) => onMessageRef.current(JSON.parse(e.data));
    return () => ws.close();
  }, [url]);  // 👈 not [url, onMessage] — would reconnect on every render
}

Stale closure

avoid
const [count, setCount] = useState(0);

useEffect(() => {
  const id = setInterval(() => {
    console.log(count);    // always logs 0 — closure captured first-render value
  }, 1000);
  return () => clearInterval(id);
}, []);  // 👈 empty deps
prefer — functional setter or ref
useEffect(() => {
  const id = setInterval(() => {
    setCount((c) => c + 1);  // functional update — no stale capture
  }, 1000);
  return () => clearInterval(id);
}, []);

// Or via ref when you need to read it
const countRef = useRef(count);
countRef.current = count;

Memoized row + stable handlers

const Row = memo(function Row({ item, onPress }: {
  item: Item;
  onPress: (id: string) => void;
}) {
  return (
    <Pressable onPress={() => onPress(item.id)} style={styles.row}>
      <Text>{item.title}</Text>
    </Pressable>
  );
});

function Screen({ items }: { items: Item[] }) {
  const onPressRow = useCallback((id: string) => console.log(id), []);

  const renderItem = useCallback(
    ({ item }: ListRenderItemInfo<Item>) => <Row item={item} onPress={onPressRow} />,
    [onPressRow]
  );

  const keyExtractor = useCallback((i: Item) => i.id, []);

  const getItemLayout = useCallback(
    (_: ArrayLike<Item> | null | undefined, index: number) =>
      ({ length: 64, offset: 64 * index, index }),
    []
  );

  return (
    <FlatList
      data={items}
      renderItem={renderItem}
      keyExtractor={keyExtractor}
      getItemLayout={getItemLayout}
      initialNumToRender={10}
      windowSize={11}
      removeClippedSubviews
    />
  );
}

Reading a flamegraph (Hermes sampling profiler)

Capture a CPU profile on-device, then read it to find the hot path — instead of guessing.

Capture

  • Dev Menu → Start Sampling Profiler; reproduce the slow interaction; Stop → writes a .cpuprofile on the device.
  • Pull it to the host (adb pull on Android; the Dev Menu surfaces the path on iOS) and open in Chrome DevTools → Performance → Load, or the Flipper Hermes debugger.
  • Profile a release build with source maps so frames are named, not minified.

Read

  • Width = time. The widest frames are where time goes; a wide leaf at the bottom is the hot function.
  • Self vs total. Total includes children, self is the function itself. Wide bar + wide child → the child is the cost. Wide bar + no children → that function is the cost.
  • Tall & thin = deep call stack (usually fine). Wide & flat = a hot loop or a function called too often.
  • Map the widest non-React frame back to a component/util. Usual culprits: JSON.parse of a large payload, an unmemoized derivation re-running each render, a comparator in a sort.

Blind spot: the Hermes profiler only sees the JS thread. If JS looks idle but frames still drop, the cost is on the UI/native side — switch to Xcode Instruments (Time Profiler) or Android Studio CPU profiler / Perfetto.

JS thread vs UI thread — proving which is starved

"How do you know it's the JS thread?" The in-app Perf Monitor (Dev Menu → Show Perf Monitor) shows two FPS numbers.

ReadingWhat it means
JS FPS low, UI FPS fineYour logic / re-renders / a large parse are blocking the JS thread. Confirm with the sampling profiler.
UI FPS also lowNative / layout / GPU work — long lists without virtualization, overdraw/shadows, oversized images.
UI fine, JS pinned during a gesture/animationThe animation is running on the JS thread — move it to the UI thread (Reanimated worklet, or useNativeDriver).

The three RN threads: JS (your code, renders, business logic), main / UI (native views, gestures, touch), shadow (Yoga layout). Crossings between them cost — that's the budget you're protecting.

"Janky only on Android" — divergence checklist

Same JS, same data, smooth on iOS, drops frames on Android. Ranked suspects:

  • Image memory. Android per-app heap is capped (often 256–512MB; largeHeap is opt-in). A decoded bitmap is W×H×4 bytes regardless of file size, so full-res photos OOM / GC-churn on Android first. Fix: explicit dimensions, server thumbnails, expo-image cache.
  • Overdraw / elevation. Shadows (elevation) and stacked translucent layers re-rasterize more expensively on Android. Use the GPU-overdraw debug overlay.
  • Entry-tier hardware. Test devices skew premium; a JS-thread budget that's fine on a flagship blows on a low-end Android chip.
  • removeClippedSubviews behaves differently per platform; toggling it can fix or cause Android-only blank cells.
  • Release-only differences. R8/ProGuard + Hermes bytecode differ from debug — always confirm jank on a release build.

Tools: Android Studio Profiler, adb shell dumpsys gfxinfo <pkg> for frame stats, Perfetto / systrace for the frame timeline.

Render fan-out — only the changed item re-renders

A dashboard of live tiles where every update re-renders ALL tiles. Subscribe each tile to only its own slice.

avoid — whole-collection selector
const all = useStore((s) => s.byId);     // new ref on any change -> every consumer re-renders
return ids.map((id) => <Tile key={id} value={all[id]} />);
prefer — per-id selector inside a memoized tile
const Tile = memo(function Tile({ id }: { id: string }) {
  const value = useStore((s) => s.byId[id]);   // re-renders only when THIS id changes
  return <Text>{value?.battery}</Text>;
});

// parent passes only ids; each tile subscribes itself
return ids.map((id) => <Tile key={id} id={id} />);

For object/array slices, add a shallow comparator (useStore(sel, shallow)) so a new wrapper ref with equal contents doesn't re-render. Pair with a non-reactive buffer that coalesces high-frequency (e.g. 5Hz) updates before they hit the store.
