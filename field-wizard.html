Multi-step Form Wizard — Composite Build

Progressive, block-by-block: one accumulated form object + a step index, per-step validation gating Next, converging on one offline-safe submit.

Architecture & build order

A single accumulated form object plus a step index are the single source of truth. Each step is a pure view over the form; canAdvance(step, form) gates Next; submit assembles the whole form and enqueues it offline-safe.

form: SiteForm   +   step: index        ← single source of truth
   ▲                    │
   │                    │
 each step writes       │ canAdvance(step, form) gates Next
 a patch (onChange)     │
                   STEPS[step] renders the active view
                        │
                   submit() → enqueue(payload, idempotencyKey)   (offline outbox)

Build order — keep something runnable at every step: render one step → step views → nav + progress → gating → submit → harden. Each step below leaves a working app.

60-min build — core vs stub

Build the core inline; leave deeper methods as stubs you flesh only if time permits. Runnable at every step; protect the last 10 min for Q&A.

Given helpers

const API_URL = 'https://example.com/api';

// validate at the boundary on the way out (one schema for the full payload)
async function postAssessment(payload: SiteForm): Promise<{ id: string }> {
  const r = await fetch(`${API_URL}/assessments`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(payload),
  });
  if (!r.ok) throw new Error(`HTTP ${r.status}`);
  return r.json();
}

const makeId = () => `a-${Date.now()}-${Math.floor(Math.random() * 1e6)}`;   // idempotency key

ATypes / data model

One flat SiteForm accumulates every step. StepKey names the steps; STEPS is the ordered list the index walks. Keeping steps in an array (not hardcoded) makes Back/Next and the progress dots fall out for free.

type SiteForm = {
  siteName: string;
  voltage: string;          // kept as string in the input; coerce on submit
  photoUris: string[];
};

type StepKey = 'details' | 'measurements' | 'photos' | 'review';

const STEPS: StepKey[] = ['details', 'measurements', 'photos', 'review'];

const EMPTY_FORM: SiteForm = { siteName: '', voltage: '', photoUris: [] };

BuseWizard skeleton — the spine

No validation or submit yet — just the index, the form, and a guarded next(). update takes a Partial<SiteForm> so each step writes only its own fields. This compiles and (after C) renders a steppable wizard.

function useWizard() {
  const [index, setIndex] = useState(0);               // ◀ which step
  const [form, setForm] = useState<SiteForm>(EMPTY_FORM);  // ◀ the one form object

  const step = STEPS[index];                            // current StepKey
  const isLast = index === STEPS.length - 1;

  // each step writes a patch — never replaces the whole form
  const update = (patch: Partial<SiteForm>) => setForm((f) => ({ ...f, ...patch }));

  const next = () => {
    if (!canAdvance(step, form)) return;                // → E gates here
    setIndex((i) => Math.min(i + 1, STEPS.length - 1));
  };
  const back = () => setIndex((i) => Math.max(i - 1, 0));

  return { index, step, isLast, form, update, next, back };
}

CStep views — controlled inputs

Each step is a dumb controlled component taking { form, onChange } — it reads its slice of the form and writes a patch up. No step owns state; they are pure views over the one form. The wizard renders exactly one by step.

type StepProps = { form: SiteForm; onChange: (patch: Partial<SiteForm>) => void };

function DetailsStep({ form, onChange }: StepProps) {
  return (
    <View>
      <Text style={styles.label}>Site name</Text>
      <TextInput
        style={styles.input}
        value={form.siteName}
        onChangeText={(t) => onChange({ siteName: t })}
        placeholder="e.g. North lot array"
      />
    </View>
  );
}

function MeasureStep({ form, onChange }: StepProps) {
  return (
    <View>
      <Text style={styles.label}>Measured voltage (V)</Text>
      <TextInput
        style={styles.input}
        value={form.voltage}
        onChangeText={(t) => onChange({ voltage: t })}
        keyboardType="numeric"
        placeholder="e.g. 240"
      />
    </View>
  );
}

function PhotosStep({ form, onChange }: StepProps) {
  const addPhoto = () =>
    onChange({ photoUris: [...form.photoUris, `photo://${form.photoUris.length + 1}`] });
  return (
    <View>
      <Text style={styles.label}>Photos ({form.photoUris.length})</Text>
      <Pressable style={styles.secondaryBtn} onPress={addPhoto}>
        <Text>Add photo</Text>
      </Pressable>
    </View>
  );
}

function ReviewStep({ form }: StepProps) {
  return (
    <View>
      <Text style={styles.label}>Review</Text>
      <Text>Site: {form.siteName || '—'}</Text>
      <Text>Voltage: {form.voltage || '—'}</Text>
      <Text>Photos: {form.photoUris.length}</Text>
    </View>
  );
}

// render the active step by key
function StepView({ step, form, onChange }: { step: StepKey } & StepProps) {
  switch (step) {
    case 'details':      return <DetailsStep form={form} onChange={onChange} />;
    case 'measurements': return <MeasureStep form={form} onChange={onChange} />;
    case 'photos':       return <PhotosStep form={form} onChange={onChange} />;
    case 'review':       return <ReviewStep form={form} onChange={onChange} />;
  }
}

DNav + progress

A WizardProgress renders one segment per step, filled up to index. The nav row shows Back (disabled on the first step), then either Next (disabled when !canAdvance) or Submit on the last step. Both are pure renders of index / isLast.

function WizardProgress({ index }: { index: number }) {
  return (
    <View style={styles.progress}>
      {STEPS.map((key, i) => (
        <View
          key={key}
          style={[styles.segment, i <= index ? styles.segOn : styles.segOff]}
        />
      ))}
    </View>
  );
}

function NavRow({
  index, isLast, canNext, onBack, onNext, onSubmit,
}: {
  index: number; isLast: boolean; canNext: boolean;
  onBack: () => void; onNext: () => void; onSubmit: () => void;
}) {
  return (
    <View style={styles.navRow}>
      <Pressable
        style={[styles.secondaryBtn, index === 0 && styles.disabled]}
        disabled={index === 0}
        onPress={onBack}
      >
        <Text>Back</Text>
      </Pressable>

      {isLast ? (
        <Pressable style={styles.primaryBtn} onPress={onSubmit}>
          <Text style={styles.primaryText}>Submit</Text>
        </Pressable>
      ) : (
        <Pressable
          style={[styles.primaryBtn, !canNext && styles.disabled]}
          disabled={!canNext}
          onPress={onNext}
        >
          <Text style={styles.primaryText}>Next</Text>
        </Pressable>
      )}
    </View>
  );
}

EValidate + submit

canAdvance is the gate Next reads — one switch over StepKey. The MVP does required-field checks; the upgrade swaps each arm for a per-step Zod schema. submit assembles the whole form into one payload, attaches a stable idempotencyKey, and hands it to enqueue (offline outbox) — never a bare POST in the component.

function canAdvance(step: StepKey, form: SiteForm): boolean {
  switch (step) {
    case 'details':      return form.siteName.trim().length > 0;
    case 'measurements': return Number(form.voltage) > 0;          // numeric + present
    case 'photos':       return form.photoUris.length > 0;         // at least one
    case 'review':       return true;                              // nothing to gate; Submit shows
  }
}

// upgrade (verbal or if time): per-step Zod schema
// const StepSchemas: Record<StepKey, z.ZodTypeAny> = { details: z.object({ siteName: z.string().min(1) }), ... };

function submit(form: SiteForm) {
  const payload = { ...form, voltage: Number(form.voltage) };      // assemble all steps into one payload
  enqueue({
    idempotencyKey: makeId(),                                      // retry-safe — server dedups
    url: `${API_URL}/assessments`,
    method: 'POST',
    body: payload,
  });
}

Because every step writes into the same form, submit needs no gathering step — the form is the payload. Coerce string inputs (voltage) to their real types only here, at the edge.

mechanismOffline enqueue (signature + minimal stub)

Field forms are filled where connectivity is unreliable, so submit must be offline-safe: persist the job, return immediately, drain on reconnect. Each job carries an idempotencyKey so a retry can't create a duplicate assessment. Generic — any feature enqueues any request. The minimal stub below just POSTs so the demo runs; the production body persists to MMKV and drains via NetInfo.

type Job = {
  idempotencyKey: string;
  url: string;
  method: 'POST' | 'PUT' | 'PATCH' | 'DELETE';
  body: unknown;
};

// signature the wizard calls — production body persists + drains on reconnect
export function enqueue(job: Job): void {
  // (prod) persist to MMKV, then void drain(); — see offline-outbox doc
  void fetch(job.url, {                                // (demo) minimal direct POST so submit fires
    method: job.method,
    headers: { 'Content-Type': 'application/json', 'Idempotency-Key': job.idempotencyKey },
    body: JSON.stringify(job.body),
  });
}

assembledFull useWizard + screen

The hook owns index + form + transitions; the screen is a pure render of it — progress, the active step, and the nav row. canNext is computed once per render and feeds the Next button's disabled state.

function useWizard(onDone: (id: string) => void) {
  const [index, setIndex] = useState(0);
  const [form, setForm] = useState<SiteForm>(EMPTY_FORM);

  const step = STEPS[index];
  const isLast = index === STEPS.length - 1;

  const update = (patch: Partial<SiteForm>) => setForm((f) => ({ ...f, ...patch }));
  const next = () => { if (canAdvance(step, form)) setIndex((i) => Math.min(i + 1, STEPS.length - 1)); };
  const back = () => setIndex((i) => Math.max(i - 1, 0));

  const submit = () => {
    const payload = { ...form, voltage: Number(form.voltage) };
    enqueue({ idempotencyKey: makeId(), url: `${API_URL}/assessments`, method: 'POST', body: payload });
    onDone('queued');                                  // optimistic — outbox owns delivery
  };

  return { index, step, isLast, form, update, next, back, submit, canNext: canAdvance(step, form) };
}

function WizardScreen() {
  const { index, step, isLast, form, update, next, back, submit, canNext } =
    useWizard((id) => Alert.alert('Submitted', `Assessment ${id}`));

  return (
    <SafeAreaView style={{ flex: 1 }}>
      <WizardProgress index={index} />
      <View style={styles.body}>
        <StepView step={step} form={form} onChange={update} />
      </View>
      <NavRow
        index={index} isLast={isLast} canNext={canNext}
        onBack={back} onNext={next} onSubmit={submit}
      />
    </SafeAreaView>
  );
}

Extensions

NeedApproach
Capture photos / scan a serialA camera step backed by expo-camera (or a QR/barcode scanner); push captured uris into form.photoUris via the same onChange patch — the step stays a pure view.
Resume a half-filled formPersist form (and index) to MMKV on every update; hydrate EMPTY_FORM from storage on mount. The single-source-of-truth shape makes this a one-line read/write.
Steps that depend on earlier answersDerive STEPS from the form instead of a constant (e.g. skip measurements when a type is "visual only"); the index logic and progress dots adapt with no other change.
Photo upload with progressUpload each photo as its own outbox job (multipart) with a per-file progress callback; the review step shows uploaded vs pending, and submit only needs the resulting uris.
Richer transitions / many fieldsSwap the two useState for a useReducer — actions like NEXT / BACK / PATCH / RESET centralize the transition rules and keep guards in one place as the form grows.
Single source of truthKeep every field in the one form object — never let a step hold its own copy, or the review/submit payload drifts from what the user sees.
