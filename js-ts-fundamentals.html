Code-only reference: closures, the event loop, promise combinators, async patterns, debounce.

Closures in loops — var vs let

A closure captures the variable binding, not a snapshot of its value — so when the callback runs decides what it reads.

var — one shared binding
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// logs 3, 3, 3

var is function-scoped, so the whole loop shares ONE i. All three callbacks close over that same binding, and they run after the loop finishes (setTimeout is async) — when i is already 3.

let — a fresh binding per iteration
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// logs 0, 1, 2

let is block-scoped, and a for loop creates a new i each iteration, so each callback captures its own. Other fixes: an IIFE per iteration, or pass the value as an argument — setTimeout((v) => console.log(v), 0, i).

Event loop — microtasks vs macrotasks

console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');
// logs A, D, C, B

Each turn: run synchronous code to completion → drain the entire microtask queue → run one macrotask → drain microtasks again → repeat.

Microtasks (drained first)Macrotasks (one per turn, after)
Promise.then/catch/finally, await continuations, queueMicrotasksetTimeout, setInterval, I/O, UI events

setTimeout(fn, 0) does not mean "run now" — it queues a macrotask, and the whole microtask queue drains ahead of it. So a resolved Promise.then always runs before setTimeout(…, 0). Code after await is a microtask. A microtask that keeps queuing microtasks can starve macrotasks.

Promise combinators

CombinatorResolvesRejects
Promise.allwhen ALL fulfill → array of valuesimmediately on the FIRST rejection (other results discarded)
Promise.allSettledwhen all settle → array of { status, value | reason }never
Promise.racewhen the FIRST settles (fulfilled or rejected)if that first one rejects
Promise.anyon the first FULFILLEDonly if ALL reject (AggregateError)
 
// all — all-or-nothing (throws if any rejects; the good results are lost)
const [a, b, c] = await Promise.all([fa(), fb(), fc()]);

// allSettled — collect everything, never throws
const results = await Promise.allSettled([fa(), fb(), fc()]);
const ok     = results.filter((r) => r.status === 'fulfilled').map((r) => r.value);
const failed = results.filter((r) => r.status === 'rejected');

// race — first to settle wins (timeout pattern)
await Promise.race([work(), timeout(5000)]);

// any — first to SUCCEED (rejects only if all fail)
await Promise.any([mirrorA(), mirrorB()]);

TypeScript: allSettled returns PromiseSettledResult<T>[]; checking r.status === 'fulfilled' narrows to { value } (vs { reason }). Results come back in input order, not completion order. Rejected/discarded promises are not cancelled — they keep running.

Serial vs parallel await

serial — sum of all latencies
for (const id of ids) {
  await fetchOne(id);            // waits for each before starting the next
}
// 5 × 200ms ≈ 1000ms; a rejection stops the loop — later ids never fire
parallel — slowest single latency
await Promise.all(ids.map(fetchOne));        // all fire at once; ≈ 200ms; fail-fast

await Promise.allSettled(ids.map(fetchOne)); // all fire; keep every result

Independent work should be parallel — an accidental for…of await is a common silent slowdown (N× the round-trips). Use serial only when each call depends on the previous result; to rate-limit, use bounded concurrency (chunk the ids and Promise.all each chunk) rather than full serial.

debounce (and throttle)

Wraps a function so it runs only after ms of silence (no further calls). The closure holds the timer; each call clears the pending one and reschedules.

function debounce<T extends (...args: any[]) => void>(fn: T, ms: number) {
  let timer: ReturnType<typeof setTimeout> | undefined;
  return function (this: unknown, ...args: Parameters<T>) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), ms);
  };
}

// with a canceller
function debounceCancelable<T extends (...args: any[]) => void>(fn: T, ms: number) {
  let timer: ReturnType<typeof setTimeout> | undefined;
  const debounced = function (this: unknown, ...args: Parameters<T>) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), ms);
  };
  debounced.cancel = () => clearTimeout(timer);
  return debounced;
}

fn.apply(this, args) forwards the arguments and this (so it works on methods) — which is why the returned function is a regular function, not an arrow. throttle runs at most once per ms (on a schedule); debounce runs after ms of quiet (waits for calls to stop). The React value-debounce hook (useDebounced) is in the React Query patterns reference.

Binary search

Three forms. The bug source is always the interval invariant — pick closed or half-open and stay consistent.

Exact find — closed interval [lo, hi]

function search(nums: number[], target: number): number {
  let lo = 0, hi = nums.length - 1;          // closed
  while (lo <= hi) {                          // <= : hi is a valid index
    const mid = Math.floor((lo + hi) / 2);    // Math.floor — JS division is float
    if (nums[mid] === target) return mid;
    if (nums[mid] < target) lo = mid + 1;
    else hi = mid - 1;
  }
  return -1;
}

Lower bound — half-open [lo, hi) — first index with nums[i] >= target

function lowerBound(nums: number[], target: number): number {
  let lo = 0, hi = nums.length;              // half-open: hi = length, not length-1
  while (lo < hi) {                           // < : hi is one-past
    const mid = Math.floor((lo + hi) / 2);
    if (nums[mid] < target) lo = mid + 1;
    else hi = mid;                            // keep mid as a candidate
  }
  return lo;                                  // = insertion point if absent
}

Search on the answer — monotonic predicate

// When feasibility is monotonic (smaller fails, larger works),
// binary-search the ANSWER space, not the array (Koko bananas, min ship capacity).
function minFeasible(lo: number, hi: number, ok: (x: number) => boolean): number {
  while (lo < hi) {
    const mid = Math.floor((lo + hi) / 2);
    if (ok(mid)) hi = mid;                    // works -> try smaller
    else lo = mid + 1;                         // fails -> go bigger
  }
  return lo;
}

Invariant: exact-find uses lo <= hi with hi = n - 1 (closed); boundary/insertion uses lo < hi with hi = n (half-open). Mixing them is the classic off-by-one. Overflow isn't a concern in JS (safe to 2^53), but always Math.floor the midpoint.
